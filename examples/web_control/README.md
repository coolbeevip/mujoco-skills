# 网页仿真工作台

在本机网页中加载 MicroDuck 场景，用按钮调用原子动作，并查看 MuJoCo 实时画面。面向学习策略控制与场景集成的开发者；运动策略在 CPU 上推理，无需 CUDA。支持步行、带球、带轮、视觉导航和办公区寻物五个预设场景，不支持上传任意 XML 或连接真实机器人。

实验性的视觉导航功能可连接多模态模型：输入自然语言任务，模型读取头部图像、选择运动目标，并在动作后重新观察。预设彩色目标支持仿真 RGB-D 测距和近距离动作门槛，不保证任意场景的到达成功率。

## 快速开始

需要 Python 3.12，以及首次安装依赖和下载模型时的网络。本机需有可用的 OpenGL 图形环境；实测为 macOS / Apple Silicon。无显示环境的 Linux 尚未验证。

从仓库根目录执行。如果已经安装并运行过 MicroDuck 样例，可以直接执行最后一行启动服务。

```sh
python3.12 -m venv examples/microduck/.venv
examples/microduck/.venv/bin/python -m pip install -r examples/microduck/requirements.txt
examples/microduck/.venv/bin/python examples/microduck/assets.py prepare
examples/microduck/.venv/bin/python examples/web_control/server.py
```

打开 <http://127.0.0.1:8766/>，选择场景并点击「加载场景」。出现机器人画面后，点击「继续仿真」，仿真时间开始增加。等待机器人站稳，再点击「前进」；点击「停止运动」回到零移动目标。

服务复用 MicroDuck 的虚拟环境与 `.cache`，不需要额外的 Web 框架、Node.js 或图像库。运行期间不下载资产。终端按 Ctrl+C 关闭服务。

## 页面操作

场景选择、加载、暂停/继续和重置位于最顶部工具条，与连接状态同排显示，不再单独占用工作区高度。

控制台采用桌面一屏布局：左侧为仿真视图，右侧通过「视觉导航 / 手动动作」TAB 切换任务表单和原子动作面板，下方共用决策记录。操作错误使用可关闭的浮动提示，不单独占用底部面板。切换 TAB 保留任务输入，不改变仿真状态，也不中止任务；导航任务期间手动动作按钮禁用，可在决策记录标题旁中止任务。TAB 获得焦点时可用左右方向键切换。窗口高度固定，长记录在面板内部滚动，不提供手机端纵向布局。建议使用至少 1280 × 720 的浏览器内容区域。

主视图右下角的「头部摄像头」画中画同时显示 640 × 360 实时图像，点击标题可收起或展开。暂停时保留画面，加载或重置场景时更新；小窗下方显示图像帧号。收起只停止小窗图像下载，不影响仿真与模型读取头部图像。主视图默认外部观察，也可以独立切换为头部视角。

| 操作 | 实际效果 |
| --- | --- |
| 选择场景 | 查看对应动作清单，尚不切换正在运行的模型 |
| 加载场景 | 停止旧场景、重建模型与控制器；新场景默认暂停 |
| 继续仿真 | 按固定控制步推进物理与策略推理 |
| 前进 / 左转 / 右转 | 设置持续移动目标，松开按钮不会停止 |
| 停止运动 | 清除移动目标，继续平衡；正在执行的一次性动作仍继续 |
| 暂停仿真 | 冻结物理时间并清除移动目标；动作进度保留，继续后接着执行 |
| 重置场景 | 清除动作、故障和物理状态，重新加载当前场景并暂停 |
| 左键拖动 / 右键拖动 / 滚轮 | 旋转 / 平移 / 缩放外部观察相机，不修改机器人物理状态 |

画面获得焦点后，也可用左右方向键旋转、加减键缩放。按钮中的字母表示与终端样例的按键对应关系，不是网页快捷键。页面固定使用标准控制台布局。

配置导航模型后，外部观察画面在机器人头顶显示模型名称，并随头部位置移动。头部摄像头和发送给模型的图像不显示该标签；未配置模型时隐藏。

视图上方的「画质」默认自动适配：根据图像显示区域和屏幕像素比选择实际渲染尺寸，最高 1920 × 1080；Retina 屏幕会请求更多像素。也可以固定选择 720p（1280 × 720）或 1080p（1920 × 1080）。旁边显示收到的图片实际分辨率，而非 CSS 显示尺寸。

画面通过 PNG 无损传输。提高分辨率会增加渲染、编码和传输开销；运行变慢时可选择 720p。调整画质不会重置机器人、动作进度或相机，暂停时也会刷新画面。自动档在窗口尺寸稳定约 350 ms 后调整，分辨率上限意味着大尺寸高像素比屏幕不一定达到逐像素显示。

动作按钮由后端生成：步行和带球场景提供移动、坐下/站起、俯身、左右脚踢球与单次翻滚；带轮场景提供轮式移动与蹲伏。移动或恢复过程中不接受新的一次性动作，页面会显示拒绝原因。坐下后再次触发可站起。动作门控、持续时间和恢复检查见 [MicroDuck 动作说明](../microduck/README.md#官方策略与动作)。

带球场景在踢球前将球放到对应脚前；不含球的步行场景仅执行踢腿。动作完成时序不代表已踢中、拾取或完成任务，需观察实际仿真结果。

## 自然语言视觉导航

先按快速开始准备仿真环境，再选择支持图像输入和 JSON 输出的模型服务。接口适配器不需要额外 Python 包。使用远程模型时，本机仅运行仿真和运动策略，不需要本地 GPU；模型服务可能按请求收费。

### 配置模型

以下命令从仓库根目录执行。将模型名替换为你有权限使用的视觉模型；配置后重启服务。启动本身不会发起模型请求。

兼容 OpenAI Chat Completions 的服务：

```sh
export VLM_PROVIDER=openai
export VLM_MODEL='替换为视觉模型名'
export VLM_BASE_URL='https://api.openai.com/v1'
# 在本机环境或 IDE 环境变量配置中设置 VLM_API_KEY。
# 使用官方 OpenAI 地址时，也可使用已有的 OPENAI_API_KEY。
examples/microduck/.venv/bin/python examples/web_control/server.py
```

`openai` 表示 OpenAI Chat Completions 兼容协议，也可连接第三方服务；旧值 `openai-compatible` 仍然兼容。第三方兼容服务需要修改 `VLM_BASE_URL` 并设置专属 `VLM_API_KEY`。适配器在基础地址后追加 `/chat/completions`，发送图像 data URL、`response_format: json_object` 和 `max_completion_tokens`；服务与模型需要支持这些参数。

已有本地 Ollama 视觉模型服务时：

```sh
export VLM_PROVIDER=ollama
export VLM_MODEL='替换为已安装的视觉模型名'
export VLM_BASE_URL='http://127.0.0.1:11434'
examples/microduck/.venv/bin/python examples/web_control/server.py
```

该适配器调用 `/api/chat`，使用图像输入和 JSON Schema 输出格式。服务与模型需提前准备，本样例不自动安装或下载。纯文本模型不能用于视觉控制，本地推理耗时取决于模型和硬件。

密钥只放在后端环境变量中，不要填写到任务框或提交到 Git。远程地址必须使用 HTTPS，本机服务允许 HTTP。只有显式设置 `VLM_PROVIDER` 和 `VLM_MODEL` 才启用模型功能，仅存在 API 密钥不会启用。

### 开始任务

1. 打开网页，确认任务区域显示配置的服务和模型名。
2. 选择「MicroDuck · 视觉导航」并加载。红色方块在机器人前方，蓝色圆柱在左后方，黄色球体在右后方，均距初始位置约 0.9 米。目标围绕机器人分布，寻找后方目标需要转身观察。
3. 通过头部画中画观察机器人视野，输入“走到红色方块前”等任务，点击「开始任务」。无需先点继续仿真。
4. 查看执行阶段、模型的可见证据和决策记录。任务期间手动动作按钮禁用；「中止任务」清除移动目标并暂停仿真。

头部视角随机器人运动，不接受拖动和缩放；切换回外部视角可自由观察。网页画质与视角不改变模型读取的头部图像。

暂停、重置、切换场景或网页心跳中断都会中止视觉任务。恢复仿真不会恢复已中止的任务，需要重新开始；已发出的模型请求可能仍产生费用，但迟到的响应不会再控制机器人。

### 办公区寻物

选择「MicroDuck · 办公区寻物」并加载。办公室为 6 × 5 米，包含四个工位、文件柜、打印区、沙发休息区，以及会议室 101、102、103。三个门洞保持开放；门口同时设置常规高度和机器人可读取的低位实体门牌。外部相机默认俯看办公室，头部相机仍受真实墙体和家具遮挡。

红、蓝、黄、绿、紫五个球的直径均为 11 厘米，顶部约到机器人腰部。球是可碰撞、可滚动的动态物体；不会在踢球前自动移动到脚边。重置恢复固定初始布局。起点只能看见红球，其他球位于身后、家具旁或会议室中，需要移动和转身探索。

可输入“找到紫色小球，走到它面前”。办公场景的模型上下文包含建筑平面图、自身位置与朝向，历史保留每次观察的位置；不提供小球隐藏坐标。彩色目标需通过深度球面校验才用于测距，绿色和紫色也支持近距离门槛。

目标不可见时，模型可以选择 `search_open`、`search_101`、`search_102`、`search_103`，分别搜索开放办公区和三个会议室，`amount=0`。控制器从该分区选择一个尚未采样且可达的观察点，根据膨胀后的墙体、固定家具碰撞地图规划路线，由现有步行策略执行，并在观察点分方向观察一圈。路线中每次停步都会检查目标；发现球后提前交回模型判断，不会直接报告任务完成。

控制器维护已采样观察点与搜索阶段，模型收到这些状态和真实定位。采样记录只说明在指定位置进行过观察，不代表家具后方或整个房间已搜索完毕。检测到连续四次转向且位置变化不足 25 厘米时，下一次重复转向会被转换为分区搜索。

路线采用“停步低头检查 → 回正头部 → 前进一段 → 再检查”的循环，行走时保持默认头部姿态。高层路线的头部切换等待 0.7～3 秒仿真时间，只有命令到位、镜头角度连续稳定且身体速度足够低才提前结束。这些调整通过现有策略执行，不直接旋转相机。模型直接要求前进或转身时，若头部尚未回正，也会先等待头部稳定再移动。

头部深度图检查前方 26 厘米宽通道内的低位障碍，并在障碍前预留 18 厘米。高层路线每次检查最多授权前进 30 厘米，且不超过已看见的连续地面距离减去 20 厘米；地面覆盖不足 50 厘米时，上限收紧为 10 厘米，无法支持最小 5 厘米动作则停止。回正期间的位移会扣除；位移超过 3 厘米或转角超过 5 度时重新检查。前进途中每 0.1 秒仿真时间复查当前视野中的深度，发现 20 厘米以内的障碍先停止，但不会因为平视时没有看到障碍就延长步长。平视不覆盖全部脚前盲区，检查后的动态变化仍可能漏检。高层路线会记录新障碍并有限重规划；路线反复停滞或运动失败会停止，不伪造成功。

高层路线的开阔直路使用 0.35 m/s 速度指令：需看到至少 60 厘米连续地面、本段至少 20 厘米、距离路线转弯点至少 50 厘米，并且检测到的前方障碍不小于 70 厘米。其他情况保持 0.3 m/s。速度指令不是保证的实际速度；手动按钮和模型直接选择的前进指令不采用这项提速。

深度检查不覆盖侧后方盲区，也不保证转身、翻滚或踢腿时不会碰到家具。办公场景允许最多 100 次模型决策、600 秒墙钟时间；一个高层搜索包含多个本地运动段，不会逐段调用远程模型。单个观察点搜索另有 300 秒仿真时间上限。跨房间自主寻物仍为实验功能，不保证任务完成。

### 控制与完成判断

模型收到任务文字、当前 640 × 360 的头部 PNG 图像、决策历史，以及当前场景的可用动作、姿态阶段和场景说明，不会收到目标物体的仿真坐标。模型可以选择移动、等待、停止、当前场景支持的原子动作、完成或中止。

### 运动中的观察

前进、转身和高层搜索期间，本地控制器每 10 个控制周期采样一次头部图像，约每 0.2 秒仿真时间一次，滚动保留最近 15 帧。采样不逐帧调用大模型；真实等待时间随机器运行速度变化，不保证墙钟 5 FPS。

任务明确指定红、蓝、黄、绿、紫中的一种颜色时，图像中新出现至少 30 个符合颜色条件的像素会触发停步复查。已持续可见的候选不会重复触发；连续 5 次运动采样不可见后才允许再次触发，避免画面边缘的步态晃动造成频繁停车。候选不需要先通过球面测距校验，因此能保留部分遮挡时的线索，但同色家具也可能误触发。身份与到达仍由模型和当前 RGB-D 门槛判断。

高层搜索即使没有发现候选，也在累计 750 个控制周期（最多约 15 秒仿真时间）后停步复查。模型再次选择同一个搜索分区时，保留当前观察点、下一航点和环视进度；不把中途复查标记为整个观察点已搜索完成。模型直接下达的移动仍受原有单段上限约束。

触发复查后先保持零速度 1 秒仿真时间，再发送两张图：第一张是停止等待后的当前图，第二张是触发时的历史图，均标注时序。历史图只提供线索，不能作为当前距离或到达证明。决策记录展示实际发送的照片与仿真时间，点击可放大；同一次请求重试沿用相同图像。照片只保留在当前任务内存中，新任务或场景重置后释放，不追加整个视频或全部历史照片到模型请求。

该机制不覆盖手动移动、踢球和翻滚等一次性动作，也不能保证不漏帧：短于采样间隔、目标像素太少、颜色不明确或完全遮挡仍可能漏检。增加复查与双图输入会增加模型调用和图像 token 消耗，模型服务需支持单次多图输入。

### 近距离到达

在「视觉导航」场景输入“找到蓝色圆柱体，走到它面前鞠躬后坐下来。你可以低头观察地面判断距离”。头部 RGB 图像负责提供目标颜色证据，MuJoCo 深度图负责测量可见表面；控制器根据相机标定与机器人自身位姿，计算躯干中心到目标表面的水平距离和方向偏差。模型不接收目标世界坐标或完整深度图，只接收测量摘要。

站姿到达门槛为表面距离 18～28 厘米、方向偏差不超过 12°。未达到时，模型过早要求鞠躬、坐下或完成，会被转换为搜索、转向或继续接近；前进量也会按剩余接近空间缩短。目标不可见不能作为到达证据。页面记录显示深度测距、方向偏差、门槛结果，以及控制器调整模型指令的原因。

本样例将“鞠躬”映射为 `ground_pick` 俯身后恢复动作，并按先鞠躬、再坐下的顺序检查。坐下会使躯干向后移；只有坐下开始前已经满足站姿门槛、当前仍保持坐姿，且表面距离不超过 38 厘米、偏角不超过 12°，才保留坐姿到达证据，避免反复站起。最终仍需要模型基于新图连续两次确认。

该功能针对任务明确指定单一颜色目标的预设视觉导航和办公区场景。颜色筛选与办公区球面校验不是通用物体识别：多个同色物体、严重遮挡、不同光照或多目标任务均不在已验证范围内。它使用模拟深度传感器，不能把效果直接等同于真实机器人单目 RGB 相机；也不提供连续避障或接触安全保证。其他场景保持原有视觉判断方式。

### 动作与执行

| 场景 | 模型可调用的原子动作 |
| --- | --- |
| 步行、带球、视觉导航、办公区寻物 | 坐下、站起、俯身、左脚踢球、右脚踢球、单次翻滚、低头、抬头、头部回正 |
| 带轮 | 蹲伏 |

可以输入“走到蓝色物体前并坐下”“坐下，然后站起”“做一次俯身动作”等任务。模型每次选择一个动作，执行结束后读取新图，再决定下一步。坐下和站起是两个明确指令：坐下完成后保持坐姿，等待和完成复核不会自行站起；移动或执行其他动作前需先站起。其他原子动作会等待策略执行及恢复阶段结束，单步上限为 30 秒仿真时间。

原子动作的 `amount` 为 0，由对应策略决定执行时序。记录中的动作完成只说明执行窗口结束，不证明踢中球、拾取或翻滚效果。俯身不含抓取；视觉导航场景中的黄色球体是固定目标，踢球动作只执行踢腿；带球场景会在踢球前自动将可运动的球放到对应脚前。组合任务不能仅因走到目标附近就判定全部完成。

「手动动作」中的低头、抬头、头部回正也可由模型调用，例如“低头看看脚前的物体”。手动调整前先停止移动并等待动作恢复；站姿和坐姿均可使用。低头和抬头设置固定的头部俯仰目标偏移（±0.35 弧度），重复触发不会累加。策略平滑调整，视觉任务等待 3 秒仿真时间后重新观察，并记录镜头相对水平的实际俯仰角。回正是恢复默认头部目标，不保证镜头严格水平。踢球、翻滚、俯身等不支持头部指令的策略接管时清除该目标；带轮场景不提供头部动作。

头部控制复用现有策略的 `head_pose` 输入，不直接覆盖关节角度，也不旋转摄像头制造低头效果。输入顺序来自固定版本的[官方推理代码](https://github.com/pollen-robotics/microduck_rl/blob/29e887ecfbf5d37144759e5a9f8a176dfb83d547/scripts/infer_policy.py)。

运动指令按目标量执行：前进计划为 5～50 厘米、左转或右转 10～60 度；等待指令为 0.2～1 秒。提示词要求模型在目标明显较远、居中且路径看起来空旷时选择 30～50 厘米，接近时选择 10～20 厘米，最后以 5～10 厘米微调；视觉远近估计不是准确测距。

模型直接选择 `forward` 时，每段最多执行 30 厘米，目标不可见或模型自评低于 60% 时最多执行 10 厘米。长计划在中途停步拍摄新图，模型重新决定继续、缩短步长、转向或停止，不自动执行剩余距离。日志显示「中途复查」和实际位移；「原计划尚余」仅是计划量减去已走距离，不是到目标物体的距离。每次模型复查也计入决策次数上限。办公区 `search_*` 的路线执行使用前述独立规则。

控制器读取机器人自身位姿，由已有 ONNX 策略控制关节，达到本段目标附近后以零速度复核 0.4～1 秒。提前结束要求连续位姿变化很小，并通过真实基座线速度、角速度及倾斜程度检查；最终位移与转角容差不变，必要的补偿会再次停步复核。转身采用轻微迈步，会伴随少量位移；高层路线的小角度偏差可在前进时修正，减少频繁停步转向。等待模型响应时冻结物理时间，网络线程不直接访问 MuJoCo。途中深度复查仅用于办公场景的前进，不构成全方向避障保证。

决策记录分别显示模型要求、实际执行结果和视觉判断，例如「左转 45°」与「实际左转 47.3° · 位移 6.3 厘米」。前进量是沿动作开始时朝向的净位移，不把身体晃动累计成行走距离。实际结果也会加入下一次模型请求。

单步复核容差为转角 5 度、前进 2.5 厘米，这是控制器的判定范围，不是精度保证。未达到目标时允许有限补偿；单步超过 10 秒仿真时间、转身净位移超过 20 厘米或前进净位移超过目标加 15 厘米时停止并报告未完成，不继续盲目尝试。

“完成”要求模型报告目标可见、置信度至少 0.8，并在停止后获取的新图上再次确认；启用近距离门槛的任务还需满足上述深度及动作顺序条件。页面显示“模型视觉确认完成”后暂停仿真。这不是通用动作效果证明，仍可能误判。默认上限为 40 次决策、300 秒墙钟时间；超时、非法输出或请求错误都会停止任务，不会被当作完成。

开始任务意味着允许向配置的模型服务发送任务、头部图像、决策历史和上述场景能力信息。服务器终端记录请求与响应，密钥会隐藏，图像 Base64 以摘要替代；日志包含任务与模型返回文字，请勿公开含私人内容的日志。请仅使用可分享的仿真内容，并确认服务的数据与计费规则。

网络连接失败、超时、HTTP 408/429 和 5xx 临时错误会自动重试，同一次观察最多请求 3 次，重试前分别等待 0.5、1 秒。输出截断可将预算从 2048 提高到 4096 重试一次，也计入这 3 次总上限。重试沿用同一张图和历史，机器人保持静止，不会重复执行动作。用户中止、任务超时或服务关闭后不再发起重试；已经发出的请求可能仍产生费用。鉴权失败、明确拒绝和非法动作输出直接停止。重试耗尽时报告失败次数和原因，任务不会被标记为完成。

## 本机运行边界

这是单用户、单场景的学习样例。多个标签页共享同一个仿真，不提供独立会话；建议只打开一个控制页面。服务只监听 `127.0.0.1`，不能作为公网服务部署。

前台页面发送心跳。关闭页面、切到后台或网络断开后，服务端在约 3 秒内暂停并清除移动目标；重新打开页面不会自动恢复。若另一个控制标签页仍在前台发送心跳，仿真会继续。

物理或渲染异常会暂停仿真并显示原因，需要显式重置。切换场景后，旧场景代号的控制请求会被拒绝。场景加载失败时旧场景也会停止，不会悄悄继续运动。

```sh
# 自定义端口或使用已准备的资产目录
examples/microduck/.venv/bin/python examples/web_control/server.py --port 9000 --cache /path/to/microduck-cache
```

## 代码阅读与扩展

点击前进后的调用顺序是：`app.js` 发送 `forward` → `server.py` 将请求交给主线程 → `scenes.py` 映射为 `w` → `Behaviors` 保存目标速度 → 每个控制步读取最新状态、执行 ONNX 推理、生成关节目标与电机力矩 → MuJoCo 推进物理 → 网页读取最新画面和状态。

| 文件 | 职责 |
| --- | --- |
| [scenes.py](scenes.py) | 场景和动作清单、MicroDuck 适配器、相机与 PNG 编码 |
| [office.py](office.py) | 办公布局、实体门牌、家具与五色动态小球 |
| [office_search.py](office_search.py) | 固定建筑碰撞地图、分区观察点、路线跟踪、覆盖记录和有限重规划 |
| [server.py](server.py) | 本机 HTTP、请求队列、故障处理、心跳与主仿真循环 |
| [navigation.py](navigation.py) | 观察、模型决策、动作执行、停止与完成复核的状态机 |
| [motion.py](motion.py) | 按实际转角和位移控制单步动作、停步复核与执行反馈 |
| [proximity.py](proximity.py) | 彩色目标 RGB-D 测距、方向与站姿近距离判定 |
| [vlm.py](vlm.py) | 模型配置、图像请求、异步网络调用与响应校验 |
| [app.js](app.js) | 生成按钮、提交请求、刷新状态与画面 |
| [display.js](display.js) | 根据视图尺寸、屏幕像素比和画质档位计算渲染尺寸 |
| [decisions.js](decisions.js) | 将动作目标、实测结果与模型证据转换为可读记录 |
| [index.html](index.html) / [styles.css](styles.css) | 页面结构、布局与交互样式 |

物理、ONNX 运动策略推理和渲染都在主线程执行，HTTP 线程只收发请求与已发布的快照；多模态模型请求在独立网络线程等待。策略控制间隔为 20 ms，每个控制步包含四个 5 ms 物理步。渲染目标间隔约 50 ms，网页约每 100 ms 读取最新状态及画面；慢机器会降低实时速度，不跳过物理步，不保证固定帧率。

新增机器人时，需要提供与 `MicroduckScene` 相同的动作、步进、状态、渲染和关闭接口，并在场景清单与工厂中注册。页面无需硬编码新机器人的关节和策略。当前工厂只接入 MicroDuck，尚未接入 Dual Piper。
